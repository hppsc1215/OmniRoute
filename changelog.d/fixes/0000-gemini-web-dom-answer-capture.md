- **fix(gemini-web):** make the browser automation actually reach Gemini again — measured 2026-11-11 against a live Pro account, four separate defects in one request path.

  **1. Answer capture.** The executor only read the reply from the intercepted `StreamGenerate` XHR. That request no longer exists on a live account: 33 intercepted `gemini.google.com` responses during one turn, none of them `StreamGenerate`, while the reply was delivered out-of-band through a service-worker fetch (invisible to `page.on("response")`) and rendered into the DOM. Every request therefore waited out its whole response window and answered `502 No response from Gemini` although Gemini had replied. `gemini-web/domAnswer.ts` now reads `<model-response>` → `message-content` → `.markdown`, accepts the text only once it is stable across consecutive polls, and refuses a container still marked `aria-busy="true"`; the network listener stays as a fast path for accounts/locales that still use it.

  **2. Consent overlay.** A fresh browser context carries no consent state, so Google's "Before you continue" dialog renders over the app inside `.cdk-overlay-container` and intercepts every pointer event — each Playwright click timed out after 30 s. `gemini-web/consent.ts` dismisses it by DOM `click()` on the reject button (a real click is exactly what the overlay swallows), best-effort: no dialog, no-op.

  **3. Model selection.** `modeSelection.ts` claimed to select a model but never clicked a menu option: it assumed a *toggle* that cycles modes, matched `button[aria-haspopup="menu"]` (which resolves to "Upload & tools" first in document order), and read an "indicator" that never changed. Models are chosen through a picker (`[data-test-id="bard-mode-menu-button"]`, aria-label "Modusauswahl öffnen, derzeit ausgewählt: …") whose `[role="menuitemradio"]` option is clicked and whose label is read back; the account remembered "Argon" from an earlier session, so no mode may be assumed active on load — every request now selects explicitly and fails closed (`unsupported_control_for_provider`) if the read-back disagrees. Measured options: "Schnellinfo 3.5 Flash-Lite", "Vielseitige Unterstützung 3.8 Flash", "Detaillierte Recherche 3.1 Pro", "Code und Analyse 4 Argon".

  **4. Stale catalog.** The registry advertised `gemini-3.1-flash-lite`, `gemini-3.7-flash` and `gemini-4-carbon`, none of which the UI offers, and omitted the live `gemini-3.8-flash` / `gemini-3.1-pro`. Registry and mode map are now the four measured modes.

  **5. Picker timing.** The composer becomes interactive ~1.2 s BEFORE the mode picker renders (measured: composer +2.4 s, picker +3.5 s after `domcontentloaded`). Selection looked the picker up once, so a request right after the composer check reported `control_not_found` and was rejected even though the app was healthy. `modeSelection.ts` now polls for the picker's existence before clicking it.

  **6. Credential decay.** Google rotates `__Secure-1PSIDTS` on the first signed-in page load, which invalidates the stored copy. The rotated jar was only merged back at the very END of a successful request, so any failure — and every load that did not reach the end — left the database holding a dead credential; the next request silently ran in the guest UI (guest menu: 3.5 Flash-Lite / 3.6 Flash / 4 Argon / 4 Carbon, no 3.8 Flash, no 3.1 Pro). The executor now persists rotated cookies immediately after the composer is ready, so the connection refreshes itself on every load.

  Thinking depth (`reasoning_effort`) is now a soft hint: the measured control is a "Denkaufwand" group inside the same picker (Niedrig/Mittel/Hoch) whose choice the picker label does not echo, so the switch is attempted and verified through the option's own `aria-checked`/`aria-selected`, and an unverifiable level is logged and ignored instead of failing a request that would otherwise succeed.
